# Spec — Direct-primitive-token-consumption audit engine

**Component:** `core-source/audit/primitive-tokens.mjs`
**Current status:** stub, no engine wired in
**Rule text:** see this package's shipped copy of `GOVERNANCE.md`, `core-source/references/non-negotiable-foundation.md`.
**Scope of this spec:** detect any direct reference to a primitive token in a component, instead of a semantic token. Distinct from the WCAG/axe-core spec and the hardcoded-styles spec.

> **Correction 2026-10-07 (human review):** the original version of this spec described a non-blocking mode for this brick. `GOVERNANCE.md` Rule 4 ("Verification") is explicit: *"A direct primitive reference fails the build — the lint's severity for this rule is blocking, never advisory"*. This spec was corrected to reflect **blocking** behavior — only the WCAG brick (`audit-wcag-axe-core.md`) stays non-blocking.

---

## 1. Framework reminder (non-negotiable, already decided)

- Foundation rule: "never consume a primitive token directly — only semantic tokens are a valid consumption" (GOVERNANCE.md Rule 4).
- The audit **always** runs, whether the public compliance badge is displayed or not.
- Engine hidden behind an **adapter interface**, replaceable without touching the rest of `core-source/`.
- **Blocking mode** for this rule: a direct primitive reference fails the build (GOVERNANCE.md Rule 4, severity always blocking, never advisory). **Human has the final word** still applies to the *content* of the report and to any documented exception (e.g. an ADR), but not to the build failure itself — no automatic fix is applied.

## 2. Objective of this brick

Scan component source code to find any reference to a primitive-level token (e.g. `--teal-500`) instead of a semantic token (e.g. `--color-interactive-text`), and produce a normalized report.

## 3. Prerequisite — primitive/semantic distinction (verified)

This module depends on a **clear primitive/semantic distinction** in the token system. Verified on 2026-10-07: this distinction is already explicit in this repository —
- `ADR-059` (3-level token hierarchy, closed) establishes the primitive → semantic → component split.
- `ADR-098` ("primitive-direct-blocking-in-ci") hardened `primitive-direct` to `severity: 'error'` in the canonical repository's own token-audit script (not shipped in this package). This protection is active today for `clone/core-source/` too — nothing exempts it, only `clone/personnalisation/branding/` is exempted — because `clone/` still lives inside that repository and is scanned by that same script. The protection disappears only once the Clone is extracted as an independent npm package and stops being scanned by it; that gap is already tracked as [issue #226](https://github.com/gnegreiros-ux/agentica-design-system/issues/226), itself blocked by the Clone's npm-packaging ticket.
- `ADR-102` (token annotation schema) gives the per-token metadata convention.

**No preliminary ticket is therefore required before this brick** — the prerequisite in section 3 of the original spec is satisfied. This brick's engine must derive its primitive/semantic map from these same token files (Style Dictionary) rather than hardcoding it, and should reuse the detection logic already built for ADR-098 where reusable, to avoid two diverging implementations of the same rule.

## 4. Adapter contract (reuses the common contract)

**Expected input:**
- path(s) or list of component source files
- the list/map of primitive tokens (derived from the token files, not hardcoded in the scanner)

**Expected output (same normalized contract as the other two specs):**
- a list of "findings": rule id, severity, location (file + line), message naming the primitive token used and the suggested semantic token if derivable, reference to the internal token documentation
- an overall status (violation count per severity)

## 5. Engine — decision to confirm

Single candidate at this stage: a **custom scanner** (regex or AST) that cross-references `var(--...)` references found in the code against the primitive-token map generated by Style Dictionary. No known third-party tool covers this exact need. To be checked against the ADR-098 implementation before writing a second implementation of the same detection.

## 6. JSON output format

```json
{
  "auditType": "primitive-tokens",
  "engine": "custom-scanner",
  "engineVersion": "x.y.z",
  "target": "component-or-file-name",
  "timestamp": "ISO-8601",
  "summary": {
    "violationsCount": 0,
    "bySeverity": { "critical": 0, "serious": 0, "moderate": 0, "minor": 0 }
  },
  "findings": [
    {
      "ruleId": "string",
      "severity": "critical | serious | moderate | minor",
      "location": "file:line",
      "message": "string",
      "suggestedToken": "string | null",
      "helpUrl": "string"
    }
  ]
}
```

## 7. Blocking behavior

- Any detected violation (`violationsCount > 0`) fails the build, per GOVERNANCE.md Rule 4.
- No automatic fix is applied — the build fails, a human fixes the source or documents an explicit exception (ADR) before re-running.

## 8. Out of scope

- WCAG audit (separate spec, non-blocking — `audit-wcag-axe-core.md`)
- Hardcoded-styles audit (separate spec, blocking — `audit-hardcoded-styles.md`)

## 9. Costs / licensing

- Custom scanner: no paid third-party dependency. Effort = development + maintenance of the primitive/semantic map as it evolves.

## 10. Acceptance criteria

- [x] The primitive/semantic distinction is confirmed explicit in the token files (ADR-059/ADR-098/ADR-102) — verified before implementation, no preliminary ticket required
- [ ] The module respects the adapter contract
- [ ] The JSON report follows the schema in section 6
- [ ] A detected violation fails the build (blocking, per GOVERNANCE.md Rule 4); no fix is applied automatically
- [ ] The detection logic is checked against ADR-098 to avoid a diverging second implementation
